> **状态**: 设计阶段
> **关联**: `docs/knowledge-base/architecture-overview/data-flows.md` Invocation Trace Capability

## 1. 用户场景

用户选择一个方法，点击"调用链追踪"，系统自动追踪从此方法开始的下游调用链，展示：

- 每个方法的入参、返回值
- 每个方法的调用耗时
- 方法间的父子调用关系（调用树）

```
UserService.getUser()  45ms  → [userId: 1] → User{id=1, name="Tony"}
  ├── UserDao.findById()  12ms  → [id: 1] → UserEntity{...}
  ├── CacheService.get()  3ms   → [key: "user:1"] → null
  └── RoleService.getRoles()  25ms  → [userId: 1] → [ADMIN, USER]
       └── RoleDao.findByUserId()  22ms  → [userId: 1] → List[2]
```

---

## 2. 与 TRACE（方法耗时）的关系

| 维度 | TRACE（方法耗时） | INVOCATION（调用链追踪） |
|------|-------------------|------------------------|
| 注入方式 | 用户选单个方法 | 自动发现并批量注入多个方法 |
| 输出 | 文本消息 | 结构化 JSON（调用树） |
| 上下文 | ThreadLocal\<Long\> | ThreadLocal\<Deque\> |
| 前端展示 | LogViewer 文本行 | TraceTreeViewer 调用树 |
| 用户感知 | "这个方法耗时多少" | "这个方法调用了谁，各自耗时多少" |

两者是**并列关系**，不是替换关系。

## 3. 核心机制（3 个通用扩展）

调用链追踪完全通过已有的插件扩展机制实现，不需要修改核心框架。但需要补充 3 个通用能力：

### 3.1 ProbeMessage 结构化输出

**问题**: 当前 ProbeMessage 只有 String payload，无法传递结构化数据。

**方案**: ProbeMessage 新增 `structuredPayload` 字段。

```java
public class ProbeMessage {
    private final String type;
    private final String payload;                    // 文本消息（兼容现有 LogViewer）
    private final Map<String, Object> structuredPayload;  // 结构化数据（新增）
    private final long timestamp;
}
```

- LOG/SNAPSHOT: structuredPayload 为 null，走现有文本渲染
- INVOCATION: structuredPayload 包含 traceId/spans，走调用树渲染

### 3.2 PluginContext 注入能力

**问题**: 插件无法在 onInject 钩子中创建关联注入点。

**方案**: PluginContext 新增 `inject()` 方法，与 `onDelete` 对称。

```java
// PluginContext 新增
String inject(InjectRequest request);  // 返回 injectionId

// ProbeHandler 新增（与 onDelete 对称）
default void onInject(PersistentInjection injection, PluginContext ctx) {}
```

- `onInject`: 核心创建主注入点后调用，插件可在此创建关联注入点
- `onDelete`: 核心删除注入点前调用，插件可在此删除关联注入点

### 3.3 PluginContext 字节码访问

**问题**: 插件无法访问目标 JVM 的类字节码，无法做调用图分析。

**方案**: PluginContext 新增字节码访问能力。

```java
// PluginContext 新增
byte[] getClassBytes(String className);      // 访问已加载类的字节码
Set<String> getLoadedClassNames();           // 获取已加载类列表
```

## 4. 数据模型

### 4.1 InvocationTrace（完整调用链）

```java
public class InvocationTrace {
    private final String traceId;          // 一次调用链唯一 ID
    private final String rootClassName;    // 根方法类名
    private final String rootMethodName;   // 根方法名
    private final long totalDurationMs;    // 总耗时
    private final long startTimestamp;      // 开始时间戳
    private final List<InvocationSpan> spans;  // 扁平 span 列表
}
```

### 4.2 InvocationSpan（单次方法调用）

```java
public class InvocationSpan {
    private final String spanId;           // 当前调用 ID
    private final String parentSpanId;     // 父调用 ID（root 为 null）
    private final String className;        // 类名
    private final String methodName;       // 方法名
    private final long durationMs;         // 耗时
    private final String args;             // 入参 JSON
    private final String returnValue;      // 返回值 JSON
    private final boolean threwException;  // 是否抛异常
    private final String exceptionMessage; // 异常信息（如果抛了）
}
```

### 4.3 ActiveInvocation（运行中调用）

```java
public class ActiveInvocation {
    private final String traceId;
    private final String spanId;
    private final String parentSpanId;
    private final String className;
    private final String methodName;
    private final long startTimeNanos;
    private final String args;             // 入参（ENTER 时捕获）
}
```

## 5. 运行时流程

### 5.1 调用图发现（注入时）

```
用户选择 getUser() → 点击"调用链追踪"
    ↓
前端发送 InjectRequest(probeType=INVOCATION, className, methodName)
    ↓
核心创建主注入点（getUser 的 method_around）
    ↓
InvocationProbeHandler.onInject(primary, ctx)
    ├── ctx.getClassBytes("UserService") → ASM 扫描 INVOKE 指令
    ├── 发现调用: UserDao.findById(), CacheService.get(), RoleService.getRoles()
    ├── 递归扫描（深度限制，默认 5 层）
    │   └── ctx.getClassBytes("RoleService") → 发现 RoleDao.findByUserId()
    └── 循环 ctx.inject(derivedRequest) → 批量创建注入点
        所有注入点共享同一个 groupId
```

### 5.2 调用树构建（运行时）

```
getUser() ENTER
  → InvocationTraceProbe.onMethodEnter("UserService", "getUser", args)
  → ThreadLocal 栈: push(traceId, spanId, parentSpanId=null)
  → 记录入参: ["userId"]

    findById() ENTER
      → onMethodEnter("UserDao", "findById", args)
      → ThreadLocal 栈: push(spanId, parentSpanId=getUser的spanId)
      → 记录入参: ["id"]

    findById() EXIT
      → onMethodExit("UserDao", "findById", returnValue)
      → pop, 记录返回值、耗时 12ms

    getRoles() ENTER → ...
    getRoles() EXIT → 25ms

  getUser() EXIT
    → onMethodExit("UserService", "getUser", returnValue)
    → pop, 记录返回值、耗时 45ms
    → 栈空 → 输出完整 InvocationTrace
```

### 5.3 InvocationContextCarrier（线程上下文）

```java
public class ThreadLocalInvocationCarrier implements InvocationContextCarrier {
    private static final ThreadLocal<Deque<ActiveInvocation>> STACK =
        ThreadLocal.withInitial(ArrayDeque::new);

    @Override
    public ActiveInvocation current() {
        return STACK.get().peek();
    }

    @Override
    public void push(ActiveInvocation invocation) {
        STACK.get().push(invocation);
    }

    @Override
    public ActiveInvocation pop() {
        return STACK.get().poll();
    }
}
```

### 5.4 InvocationTraceProbe（Bootstrap 类）

```java
public class InvocationTraceProbe {
    // method_around ENTER 时调用
    public static void onMethodEnter(String className, String methodName, Object[] args) {
        // 1. 获取 carrier
        // 2. 如果栈空 → root → 生成 traceId
        // 3. 如果栈非空 → parentSpanId = current.spanId
        // 4. 序列化入参（防御式）
        // 5. 生成 spanId，push ActiveInvocation
    }

    // method_around EXIT 时调用
    public static void onMethodExit(String className, String methodName, Object returnValue, Throwable thrown) {
        // 1. pop ActiveInvocation
        // 2. 计算 durationMs
        // 3. 序列化返回值（防御式）
        // 4. 创建 InvocationSpan
        // 5. 如果栈空 → root EXIT → 输出完整 InvocationTrace
        //    否则 → span 加入 pending 列表
    }
}
```

## 6. 入参/返回值序列化

复用 SnapshotSerializer 的防御式策略：

| 类型 | 策略 |
|------|------|
| 基本类型 | 直接序列化 |
| String | 截断超长值（默认 256 字符） |
| 对象类型 | toString()，截断 |
| 集合类型 | size + 前 N 个元素（默认 N=5） |
| Map 类型 | size + 前 N 个 entry |
| null | "null" |
| 业务异常 | 捕获并返回 "[serialization error: className]" |

## 7. 静态调用图分析

### 7.1 StaticCallGraphAnalyzer

```java
public class StaticCallGraphAnalyzer {
    private final PluginContext ctx;
    private final int maxDepth;

    public CallGraph analyze(String className, String methodName, String methodDesc) {
        // 1. ctx.getClassBytes(className) 获取字节码
        // 2. ASM 扫描方法体中的 INVOKE 指令
        // 3. 递归分析被调用方法（深度 maxDepth 限制）
        // 4. 返回 CallGraph（树形结构）
    }
}
```

### 7.2 局限性

| 局限 | 说明 | Phase 1 处理 |
|------|------|-------------|
| 多态 | `animal.speak()` 只能看到 Animal.speak | 扫描所有已知子类同名方法，全部注入 |
| 反射 | `Method.invoke()` 看不到实际调用 | 不支持，UI 提示 |
| Lambda | invokedynamic 指令 | 通过合成方法名 `lambda$xxx$N` 追踪 |
| 接口 | 调用接口方法 | 扫描所有已知实现类 |
| JDK 类 | java.lang.* 等 | 默认跳过，不注入 JDK 类 |

### 7.3 过滤策略

```java
public class CallGraphFilter {
    private static final Set<String> SKIP_PREFIXES = Set.of(
        "java.", "javax.", "sun.", "com.sun."
    );

    boolean shouldTrace(String className) {
        // 跳过 JDK 类、Luna 自身类
        for (String prefix : SKIP_PREFIXES) {
            if (className.startsWith(prefix)) return false;
        }
        return !className.startsWith("fun.efto.luna.");
    }
}
```

## 10. 深度控制与治理

### 10.1 静态深度（注入时）

- `maxDepth` 参数控制调用图分析的最大递归深度（默认 5）
- 超过深度的方法不注入
- 用户可在 configSchema 中调整

### 10.2 运行时深度（运行时）

- ThreadLocal 栈最大深度限制（默认 20，防止递归溢出）
- 超过深度的调用不 push，但 root 仍能正常 EXIT

### 10.3 消息背压

- 一次调用链输出一个 InvocationTrace（root EXIT 时一次性发送）
- 如果 RingBuffer 满则丢弃整个调用链
- 不会出现"半截调用树"的情况

## 12. 风险分析

| 风险 | 说明 | 应对 |
|------|------|------|
| 性能 | 批量注入多个方法，retransform N 次 | 可优化为批量 retransform，Phase 1 先逐个 |
| 数据量 | 高频方法产生大量 InvocationTrace | 采样策略 + RingBuffer 背压 |
| 递归 | 递归方法导致 ThreadLocal 栈溢出 | maxDepth 限制 |
| 多态 | 静态分析看不到实际调用 | 扫描所有已知子类 |
| 反射 | 无法追踪反射调用 | UI 提示，Phase 2 可能支持运行时拦截 |
| 入参序列化 | 大对象序列化影响性能 | 防御式截断 + 长度限制 |
| ThreadLocal 泄漏 | 异常退出时 pop 未调用 | AROUND 语义保证 EXIT 阶段执行 |

---

## 13. 不在 Phase 1 范围

- 异步/跨线程传播（InvocationContextCarrier.propagate）
- 火焰图可视化
- Pattern 匹配自动注入（如 `com.example.service.*`）
- ObservationStore 持久化
- AI 诊断
- 采样策略（Phase 1 全量采样）
