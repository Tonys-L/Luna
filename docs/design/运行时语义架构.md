# Luna Runtime Semantic Architecture

> 日期：2026-05-30
> 状态：Draft
> 作者：Luna Runtime Diagnostics
> 目标：定义 Luna Runtime Semantic Architecture，用于统一 Runtime Instrumentation、Invocation Trace、Variable Capture、Visualization、Explainability、AI Diagnostics 的核心运行时语义模型。

---

# 1. 为什么需要 Runtime Semantic Architecture

传统 Java Agent 通常基于：

```text
class + method + line
```

进行定位。

例如：

```text
OrderService#create:42
```

但：

这种模型存在根本问题。

---

# 1.1 JVM 并不理解源码行

JVM Runtime 真正理解的是：

* bytecode
* operand stack
* local variable slot
* frame
* control flow

而不是：

```text
源码 line
```

---

# 1.2 line number 并不是 Runtime Truth

line number：

只是：

# 调试投影（Debug Projection）

来源于：

```text
LineNumberTable
```

它：

* 不稳定
* 不唯一
* 不精确
* 可能缺失
* 可能漂移

因此：

```text
line != runtime semantic position
```

---

# 1.3 Decompiled Source 不是 Original Source

反编译：

不是：

```text
源码恢复
```

而是：

```text
源码重建
```

因此：

* line 会变化
* control flow 会变化
* lambda 会漂移
* finally 会复制
* invoke order 会变化

---

# 1.4 Runtime Diagnostics 的核心不是 “代码行”

真正重要的是：

* invoke relation
* execution flow
* causality
* blocking
* runtime state
* frame state

因此：

Luna 需要建立：

# Runtime Semantic Architecture

作为：

* instrumentation
* diagnostics
* explainability
* visualization
* AI reasoning

的统一 Runtime Truth Layer。

---

# 2. 核心思想

---

# 2.1 Runtime Truth First

Luna 的核心原则：

```text
Runtime Truth
    -> Projection
        -> Source
        -> Decompiled Source
        -> Editor
        -> Visualization
```

而不是：

```text
Source
    -> Runtime
```

---

# 2.2 Source 只是 Projection

source：

不属于 runtime core。

source：

只是：

# Human-readable Projection

---

# 2.3 Runtime Semantic Boundary

Luna 不围绕：

```text
line
```

建立能力。

而围绕：

# Runtime Semantic Boundary

建立能力。

例如：

* method entry
* invoke before
* invoke after
* return
* exception throw
* monitor enter
* monitor exit

---

# 2.4 Semantic Boundary != Physical Injection Point

用户想表达的是：

# Semantic Intent

但：

真正插桩的位置：

必须：

* verifier-safe
* frame-safe
* stack-safe

因此：

```text
semantic boundary
!=
physical probe point
```

---

# 3. 整体架构

---

# 3.1 Architecture

```text
Bytecode Layer
    -> Runtime IR
        -> Control Flow Graph
            -> Semantic Boundary
                -> Probe Point
                    -> Execution Event
                        -> Observation Graph
                            -> Projection Layer
```

---

# 4. Bytecode Layer

Bytecode Layer 属于：

# JVM Physical Representation

---

# 4.1 包含内容

* instruction
* frame
* stack map frame
* local slot
* jump
* exception table

---

# 4.2 不直接暴露给上层

Runtime Semantic System：

不应直接依赖：

```text
ASM instruction tree
```

否则：

* instrumentation fragile
* compiler coupling
* verifier complexity

会不断恶化。

---

# 5. Runtime IR

这是整个系统的核心。

---

# 5.1 为什么需要 Runtime IR

Bytecode：

属于：

# JVM Execution Representation

而不是：

# Runtime Semantic Representation

例如：

```java
foo(bar(x));
```

Bytecode：

可能是：

```text
ALOAD
INVOKEVIRTUAL
ALOAD
INVOKEVIRTUAL
```

但：

Runtime Diagnostics 真正关心的是：

* invoke relation
* execution boundary
* causality

因此：

必须建立：

# Runtime IR

---

# 5.2 Runtime IR 的目标

Runtime IR：

负责：

* semantic normalization
* compiler abstraction
* control flow representation
* runtime boundary representation

---


* frame 不兼容

```text

```

```java

}
```

因此：

静态 boundary：

不能代表：

# Runtime Execution Instance

# 11. Variable Lifetime Model

本质上：

# slot lifecycle

而不是：

# source variable

# 11.1 slot reuse

例如：

```java

   int a = 1;
}

{
   String b = "x";
}
```

可能：

```text
a 与 b 使用同一个 slot
```

因此：

slot：

不能直接视为 variable。

---

# 11.2 Variable Version

# Variable Lifetime Version

```text

```
