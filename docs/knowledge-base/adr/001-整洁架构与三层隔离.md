# ADR-001: 整洁架构与三层隔离

## 状态

Accepted

## 背景

Luna 作为 Java Agent 运行在目标 JVM 中，核心业务逻辑（注入模型、插件管理、表达式求值）不应依赖具体技术实现（ASM/Jetty/CFR）。如果核心层直接依赖 ASM 的 Visitor API、Jetty 的 Servlet API 或 CFR 的反编译 API，未来替换底层技术时将导致核心业务逻辑大面积修改。

同时，Luna 需要确保业务不变量（如"注入代码异常不能传播到业务代码"、"RingBuffer 满时丢弃不阻塞业务线程"）在核心层得到保护，不受技术实现变化的影响。

## 方案选项

### 选项 A: 传统分层架构

采用表现层/业务层/数据层的传统分层架构，依赖方向从上到下流动。

优点：
- 开发者熟悉，上手成本低
- 层次清晰，职责直观

缺点：
- 核心业务逻辑依赖技术实现（ASM/Jetty/CFR），替换底层技术时核心层必须修改
- 业务不变量分散在各层，无法集中保护
- 技术实现变更会波及核心层，违反"核心层稳定"原则

### 选项 B: 整洁架构与三层隔离

采用整洁架构（洋葱架构），依赖方向向内流动。将系统分为三层：

- **策略层（易变）**：路由策略、调度策略、重试策略、采样策略、选择逻辑
- **核心层（稳定）**：能力契约、领域模型、业务规则、不变量
- **实现层（可替换）**：存储实现、通信实现、字节码操作实现、第三方系统接入

核心层禁止出现 SQL/Redis/MQ/HTTP/RPC/框架基础设施代码，只表达业务语义。

优点：
- 核心层稳定，技术实现可替换
- 业务不变量在核心层集中保护
- 实现层可独立替换，不影响核心语义
- 符合"业务优先于技术"的设计原则

缺点：
- 接口抽象层增加代码量
- 需要定义 Port 接口（如 Retransformer、InjectionStore、BytecodeLoader、InjectionVerifier），由外层提供实现
- 开发时需严格遵守依赖方向约束

## 决策

选择**选项 B：整洁架构与三层隔离**。

核心业务逻辑是 Luna 最有价值的部分，必须保持稳定。技术实现（ASM 版本升级、Web 服务器替换、反编译引擎切换）是可预期的变化方向，通过三层隔离确保这些变化不波及核心层。接口抽象层增加的代码量是控制变更成本的合理代价。

## 影响

- 核心层代码（luna-core 的核心包）禁止出现任何技术实现相关的 import（ASM、Jetty、CFR 等）
- 核心层通过 Port 接口与外层协作，外层提供实现
- 未来替换底层技术（如 ASM 版本升级、Jetty 替换为其他 Web 服务器）时，只需修改实现层，核心层无需变更
- 开发时需严格遵守依赖方向：策略层 → 核心层 ← 实现层
