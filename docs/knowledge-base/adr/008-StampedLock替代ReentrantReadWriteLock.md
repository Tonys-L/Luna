# ADR-008: StampedLock替代ReentrantReadWriteLock

## 状态

Accepted

## 背景

Luna 的插件管理模块存在典型的读写并发场景：

- **写操作（独占）**：插件加载/卸载时，需要修改插件注册表、注入点映射等数据结构
- **读操作（并发）**：注入操作执行时，需要查询当前活跃的注入点、插件状态等信息

读操作远多于写操作（每次方法调用都会触发注入查询），使用 ReentrantReadWriteLock 会导致读操作之间也存在锁竞争（通过 CAS 维护共享的 state 变量），在高并发注入场景下成为性能瓶颈。

## 方案选项

### 选项 A: 使用 ReentrantReadWriteLock

采用传统的 ReentrantReadWriteLock 实现读写分离。

优点：
- API 简单，开发者熟悉
- 支持锁重入
- 支持锁降级（写锁降级为读锁）

缺点：
- 读操作之间存在 CAS 竞争（共享 state 变量）
- 高并发读场景下吞吐量受限
- 非公平模式下可能出现写饥饿

### 选项 B: 使用 StampedLock 实现乐观读锁

使用 StampedLock 的乐观读模式，读操作先尝试乐观读（无锁），验证失败再升级为悲观读锁。

优点：
- 乐观读零开销，不修改共享状态，吞吐更高
- 适合读多写少的场景（注入查询远多于插件加载/卸载）
- 写操作不会被读操作阻塞

缺点：
- API 复杂度略高（乐观读 → 验证 → 悲观读的流程）
- 不支持锁重入
- 不支持锁降级
- 使用不当可能导致活锁

## 决策

选择**选项 B：使用 StampedLock 实现乐观读锁**。

Luna 的注入查询场景是典型的读多写少：每次业务方法调用都会触发注入查询，而插件加载/卸载是低频操作。StampedLock 的乐观读模式在无写操作时完全零开销，显著提升注入查询的吞吐量。API 复杂度略高是合理的性能代价。

## 影响

- 插件管理模块使用 StampedLock 替代 ReentrantReadWriteLock
- 注入查询使用乐观读模式，验证失败时升级为悲观读锁
- 插件加载/卸载使用写锁（独占）
- 需注意 StampedLock 不支持重入，同一线程不可重复获取写锁
