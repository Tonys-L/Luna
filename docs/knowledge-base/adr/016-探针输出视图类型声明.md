# ADR-016: 探针输出视图类型声明

## 状态

Proposed

## 背景

ADR-015 解决了前端**注入配置侧**的硬编码问题（快捷菜单、注入对话框、探针元数据），但**输出渲染侧**仍存在硬编码：

1. **LogViewer.vue 硬编码渲染分支**：使用 `v-if/v-else-if` 硬编码 `SNAPSHOT/INVOCATION/其他` 分支，新增探针类型必须修改 LogViewer。

2. **消息分发硬编码**：`messageHandlers` 对象硬编码 `SNAPSHOT/TRACE/LOG/INVOCATION` 四种消息类型，无法扩展。

3. **视图组件硬绑定**：`TraceTreeViewer` 直接 import 并在 `v-else-if="log.type === 'INVOCATION'"` 中使用，而非根据后端元数据动态选择。

根因：ProbeHandler 缺少输出视图类型声明，前端无法知道某种探针类型的数据应使用哪种渲染方式。

## 方案选项

### 选项 A：前端配置文件映射

在前端 `plugin-registry.js` 中硬编码 `probeType → viewType` 映射。

优点：
- 改动最小

缺点：
- 新增探针类型仍需修改前端配置
- 前后端数据分散，容易不一致
- 违反"插件自包含"原则

### 选项 B：ProbeHandler 声明输出视图类型 + API 暴露 + 前端数据驱动（推荐）

ProbeHandler 新增 `getOutputViewType()` 方法，ui-manifest API 暴露，前端根据视图类型分发渲染组件。

优点：
- 新增探针类型复用已有视图类型时，前端零改动
- 单一数据源（后端 ProbeHandler），前后端一致
- 符合 ADR-015 的数据驱动方向
- 视图类型为有限集合（text/snapshot/tree），前端维护映射表成本可控

缺点：
- 新增视图类型仍需前端添加组件（但这是合理成本，不是每个探针都需要新视图类型）

### 选项 C：插件自定义前端渲染组件

插件注册时提供前端组件 URL，前端动态加载渲染。

优点：
- 完全插件自包含

缺点：
- 过度设计（YAGNI），当前无第三方插件需要
- 涉及动态组件加载、沙箱隔离、版本兼容等复杂度
- 违反"禁止一步到位抽象"原则

## 决策

选择选项 B。

理由：
1. 当前只有 4 个内置探针、3 种视图类型（text/snapshot/tree），选项 C 的复杂度不必要。
2. 遵循三次法则：第一次（INVOCATION 用 tree）直接实现即可，等出现真实的第三方插件需要自定义渲染时再抽象。
3. 选项 B 与 ADR-015 一脉相承，补齐输出渲染侧的数据驱动能力。

## 影响

### 后端变更

#### 1. ProbeHandler 新增 1 个 default 方法

```java
public interface ProbeHandler {
    // ... 现有方法不变 ...

    /**
     * 探针输出数据的视图类型。
     * 前端根据此值选择渲染组件。
     * 有限集合：text / snapshot / tree
     * - text: 纯文本渲染（默认）
     * - snapshot: 快照链接 + 详情面板
     * - tree: 调用树渲染
     */
    default String getOutputViewType() { return "text"; }
}
```

#### 2. 内置插件实现

| 插件 | outputViewType | 理由 |
|------|---------------|------|
| LogProbeHandler | "text"（默认） | 纯文本输出 |
| SnapshotProbeHandler | "snapshot" | 快照链接 + 详情面板 |
| TraceProbeHandler | "text"（默认） | 纯文本输出（耗时信息） |
| InvocationProbeHandler | "tree" | 调用树渲染 |

#### 3. UiManifestVO.ProbeTypeEntry 新增字段

```java
public static class ProbeTypeEntry {
    // ... 现有字段不变 ...
    private final String outputViewType;
}
```

#### 4. PluginUIController 传入

```java
.map(h -> new UiManifestVO.ProbeTypeEntry(
    // ... 现有参数不变 ...
    h.getOutputViewType()))
```

### 前端变更

#### 1. plugin-registry.js 读取 outputViewType

```javascript
_convertToProbeTypes(probeTypes) {
    return probeTypes.map(p => ({
        // ... 现有字段不变 ...
        outputViewType: p.outputViewType || 'text'
    }))
}
```

#### 2. LogViewer.vue 重构渲染逻辑

**消息处理**：从 plugin-registry 查找 `probeType → outputViewType` 映射，存入 log 对象。

**模板渲染**：根据 `outputViewType` 分发到对应组件：

```html
<!-- 替换现有的 v-if/v-else-if 硬编码链 -->
<template v-if="log.outputViewType === 'tree'">
  <span class="log-tag tag-invocation">TRACE</span>
  <span v-if="log.timestamp" class="log-time">{{ formatTime(log.timestamp) }}</span>
  <div class="log-content invocation-content">
    <TraceTreeViewer :trace="log.trace" :timestamp="log.timestamp" />
  </div>
</template>
<template v-else-if="log.outputViewType === 'snapshot'">
  <span class="log-tag tag-debug">DEBUG</span>
  <span v-if="log.data && log.data.timestamp" class="log-time">{{ formatTime(log.data.timestamp) }}</span>
  <span class="log-content snapshot-link" @click="openDebugger(log.data)">
    <i class="fas fa-bug"></i> 触发虚拟断点快照: {{ (log.data.payload && log.data.payload.pointId) || log.data.pointId }} (点击查看详情)
  </span>
</template>
<template v-else>
  <!-- text: 通用文本渲染 -->
  <span class="log-tag" :class="getTypeConfig(log.type).tagClass">{{ getTypeConfig(log.type).tag || log.type }}</span>
  <span v-if="log.timestamp" class="log-time">{{ formatTime(log.timestamp) }}</span>
  <span class="log-content" :class="getTypeConfig(log.type).contentClass">{{ log.text }}</span>
</template>
```

### 开发计划

| 步骤 | 内容 | 验证方式 |
|------|------|----------|
| 1 | ProbeHandler 新增 `getOutputViewType()` | 编译通过 |
| 2 | 内置插件覆写 | InvocationProbeHandler→"tree", SnapshotProbeHandler→"snapshot" |
| 3 | UiManifestVO.ProbeTypeEntry 新增 outputViewType | 编译通过 |
| 4 | PluginUIController 传入 outputViewType | API 返回新字段 |
| 5 | plugin-registry.js 读取 outputViewType | 控制台验证 |
| 6 | LogViewer.vue 重构渲染逻辑 | 手动测试 4 种探针类型输出正常 |

回滚方案：所有变更向后兼容（default 方法、API 新字段前端兜底），降级时 `outputViewType` 默认 `"text"` 走原有逻辑。

### 风险分析

| 风险类型 | 风险描述 | 应对措施 |
|----------|----------|----------|
| 兼容性 | ProbeHandler 新增 default 方法 | 所有新方法有默认实现，现有插件无需修改 |
| API 兼容 | ui-manifest 返回新字段 | 前端用 `p.outputViewType \|\| 'text'` 兜底 |
| 视图类型扩展 | 新增视图类型需前端添加组件 | 合理成本，当前只需 3 种 |

### 演进方向

当出现**真实的**第三方插件，其输出数据结构无法被 text/snapshot/tree 覆盖时，再考虑：
- 插件通过 API 声明 `viewComponentUrl`（远程组件 URL）
- 或插件 JAR 内含前端资源，agent 提供静态文件服务

当前不为此设计（YAGNI）。
